## 第 0 章 全景：这是一套什么系统

**先修**：无。

### 0.1 RAG 是什么

RAG（Retrieval-Augmented Generation，检索增强生成）= 先检索、后生成。
回答用户问题前，系统先从知识库里**检索**出最相关的原文片段（证据），
再把这些证据交给大语言模型（LLM）**生成**回答。LLM 只负责组织语言，不负责记忆——
它的知识全部来自检索到的证据，因此可以引用页码、避免胡编（幻觉）。

### 0.2 本项目的数据流

```
PDF 手册 ──入库──> 切块 ──> 每块算 embedding 向量 ──> 发布为「索引代」
                                                          │
用户问题 ──────────检索──────────────────────────────────> │
                     ├─ 中文全文检索（PostgreSQL tsvector）
                     ├─ 向量检索（余弦相似度）
                     └─ 两路融合（RRF）──> top-k 证据 ──> (可选) rerank 重排
                                                          │
                                                    LLM 引用证据生成回答
```

核心库 `know_one` 的关键模块：

| 模块 | 职责 |
|---|---|
| `know_one/ingestion/pdf.py` | PDF 来源与解析（字节快照、页码定位） |
| `know_one/core/api.py` | 入库→切块→embedding→发布流水线 + 检索门面（`KnowOne` 类） |
| `know_one/embedding.py` | OpenAI 兼容 embedding 客户端（批量、超时预算） |
| `know_one/full_text.py` | 中文全文检索支持 |
| `know_one/rerank.py` | LLM 重排（后加，见第 5-6 章） |
| `know_one/eval/smoke.py` | 检索评测 CLI |

### 0.3 三种检索模式

| 模式 | 原理 | 特点 |
|---|---|---|
| `full_text` | 中文分词 + PostgreSQL 全文匹配 | 精确词命中强，但换说法就找不到 |
| `vector` | 问题与块的 embedding 余弦相似度 | 语义相近能召回，但细粒度区分弱 |
| `hybrid` | 两路各取候选，RRF 融合排名 | 互补，是部署口径 |

**RRF（Reciprocal Rank Fusion，倒数排名融合）**：不用分数只用排名，
每路的块得分 = `权重 / (60 + 排名)`，60 是社区通用常数。
本项目全文路权重为 **0.25**（这个数字怎么来的，见第 2 章）。
RRF 的优点是对分数分布不敏感（全文分和余弦分根本不可比），缺点是
「两路都不错但都不拔尖」的块可能赢不过「单路第一」的块——这正是后文 rerank 的动机。

### 0.4 怎么判断「检索好不好」

评测口径：对每道人工标注的题（问题 + 期望短语 + 期望页码），
看**期望短语所在块**是否出现在检索结果的 top-k（评测默认 k=8）内。
出现即命中（hit），未出现即 miss，并记录该块实际排在第几（rank，r1=第一名）。
「r12」的意思是：正确答案块排第 12 位，没进 top-8，这题 miss。

## 第 1 章 评测先行：护栏思维

**先修**：第 0 章。

### 1.1 为什么先建评测集再改代码

调检索系统有个天然陷阱：任何改动都可能「修好 A 题弄坏 B 题」。
如果每次只手工试几道题，你永远不知道全局是变好还是变坏。
所以本项目所有优化都遵循一条纪律：

> **改动前先有一组「锁定集」（locked eval set），任何改动后全量回归，
> 分数不降才能合入。**

### 1.2 锁定集长什么样

`examples/rav4/eval/hybrid_smoke.jsonl` 每行一题：

```json
{"id": "rav4-smoke-key-001", "query": "钥匙没电了怎么启动？",
 "recall_threshold": 8,
 "expected_any": ["将钥匙顶住……"],   // 期望短语：必须逐字出现在某块原文中
 "expected_pages": [92],              // 期望页码
 "review_status": "approved"}         // 人工复核状态
```

要点：

- **expected_any**：短语是从手册原文逐字摘的（不是转述），
  判定时用「去空白后的子串包含」**精确匹配**（PDF 文本层常有中文硬换行）。
  数组内多短语是 OR（任一命中即可）；跨块答案另用可选字段
  `expected_context_any` 作 AND 附加条件（见 2.1）。
  判卷故意不用向量相似度：评测器必须独立于被测系统，且可复现。
- **recall_threshold**：即 top-k。
- **review_status**：`draft`（自动校验过）→ `approved`（人工复核过），
  只有 approved 才升级为 `_v1` 版本化锁定集（见第 8 章）。

### 1.3 四个锁定集 = 四道护栏

| 锁定集 | 条数 | 口径 | 底线 |
|---|---|---|---|
| `hybrid_smoke.jsonl` | 22 | 裸基线（无词典无 rerank） | hybrid 22/22 |
| `hybrid_golden_v1.jsonl` | 30 | 词典 + rerank | 30/30 |
| `gasoline_smoke_v1.jsonl` | 18 | 汽油手册，裸基线 | hybrid+rerank 18/18 |
| `answer_smoke.jsonl` | 5 | 回答链路引用正确 | 5/5 |

**学习要点**：护栏的「口径」必须标注清楚——裸基线集不能混用词典/rerank 来跑，
否则你测的不是索引质量而是外加机制的质量，两件事不可比。

## 第 2 章 第一轮质量问题：三种病，三种药

**先修**：第 0、1 章。

锁定集跑起来后暴露的第一批 miss，各自病因不同，**药也完全不同**。
这一章的价值在于：同一个症状（miss），背后可能是数据问题、参数问题、词汇问题。

### 2.1 病一：答案跨块 → 修口径（key-battery）

- **症状**：问钥匙电池，检索明明把两个相关块都找回来了，评测却判 miss。
- **诊断**：手册把「拆卸步骤」和「注意事项」写在相邻两块，没有任何一块
  单独包含完整期望短语。
- **药**：不是改检索，是改**评测口径**——`expected_any` 改为多短语 AND 语义：
  每个短语各自能在**某个**召回块中找到即可，不要求同块。
- **学习要点**：先分清「检索错了」还是「判定标准错了」。改判定标准要有理由
  （手册原文确实分块），不能为了分数好看而放宽。

### 2.2 病二：全文路权重过大 → 调参数（security-001）

- **症状**：hybrid 模式下安全类问题 miss，但单独跑 vector 路是命中的。
- **诊断**：手册中「安全」是个高频词，全文路把一堆含「安全」的块排得很高，
  RRF 融合时把语义更准的向量路结果挤出 top-k。
- **药**：全文路 RRF 权重从 0.30 降到 **0.25**。实测 0.30 是红线——0.30 时该题
  挤出，0.25 时回来，且全量回归不掉题。
- **学习要点**：融合权重是「两路的相对话语权」，没有理论最优值，
  只能靠锁定集实测找拐点。**每调一次都要全量回归**，防止按下葫芦浮起瓢。

### 2.3 病三：口语词 ≠ 手册术语 → 词典扩展（signal-001）

- **症状**：问「转向灯」，vector/hybrid 都 miss；把问题换成「转向信号灯」立即命中。
- **诊断**：手册用语是「转向信号灯」，用户口语是「转向灯」。embedding 有一定
  语义泛化能力，但手册里大量无关「信号」词汇干扰下泛化不够。
- **药**：**查询扩展词典** `query_expansions.json`：
  `转向灯 → 转向信号灯`、`挡 → 档位`。检索前把问题补全成手册语言。
- **架构决策**：词典放在**调用方层**（examples 下的评测脚本/回答脚本自己加载拼接），
  而不是核心库 `know_one/retrieve`。理由：词典是「某本手册的语言习惯」，
  属于数据而非库的职责；核心库不认识任何具体手册。
- **学习要点**：口语与术语的鸿沟是中文 RAG 的常见病；修在查询侧（便宜、无风险）
  而不是索引侧（贵、全局影响）。这个「调用方组合层」的模式后面还会出现（rerank）。

## 第 3 章 块污染根治：transmission-001 与 v3-table 切块

**先修**：第 0 章（数据流）、第 2 章（诊断思路）。这是全项目最精彩的一次排查。

### 3.1 症状与初步排除

- **症状**：hybrid 22 题锁定集中，transmission-001（变速箱问题）稳定 miss，
  正确块排在 **r12**，top-8 之外。词典无效、权重无效。
- **排除**：vector 单路也是 r12 左右 → 不是融合问题，是**这个块本身在向量空间
  就不像这个问题**。问题出在数据（块内容），不在算法。

### 3.2 诊断工具：SQL 直查

不依赖检索接口，直接查数据库看块的原文：

```sql
-- 关键技巧：块原文含换行，用 regexp_replace 抹掉空白再 LIKE，可跨行匹配
SELECT id, left(raw_text, 200), char_length(raw_text)
FROM chunk
WHERE regexp_replace(raw_text, '\s', '', 'g') LIKE '%目标短语%';
```

（注意：chunk 表本身没有 namespace_id 过滤条件，别画蛇添足加错。）

一查吓一跳：目标答案埋在一个 **4000+ 字的大块**里——章节标题、正文、
注意事项、表格全部挤在同一个块里。embedding 是把整块文本压成一个向量，
4000 字的「大杂烩」向量在语义空间里什么都不像 → 这就是**块污染**（chunk pollution）：
一个块混入了太多不相关内容，把自己的语义信号稀释了。

### 3.3 病根：为什么切块没切开

当时的切块规则（v1）按字符数上限切（`PDF_CHUNK_MAX_CHARS=400`）+ 大标题边界。
但丰田手册的排版是：大标题（「N.标题」）下面直接跟小节，
**小节标题是「N-N.」形式的次级编号**，v1 不认它；表格行也不认。
于是「标题 8.1 + 8.2 + 8.3 + 表格 + 注意事项」全被并进一个超长块。

### 3.4 手册的隐藏结构：■ 和 ●

人眼看手册，每个条目前面有 **■（黑色实心方块，U+25A0，Python 里 `chr(9632)`）**
和 ●（实心圆点）标记。这是丰田手册的条目分隔体系——**版式本身就是语义边界**。

> 插曲：这里出过一次误判——把 ■（U+25A0）和 □（U+25B2 空心方块 U+25A1，
> `chr(9633)`）搞混，一度以为汽油手册没有 ■ 体系。教训：
> **Unicode 字符不要靠眼睛认，用 `ord()`/`chr()` 确认码点。**

### 3.5 三轮实验：v2 → v3-table

- **v2（■ 边界版）**：遇到 ■ 就切。transmission-001 从 r12 → 大幅提前，
  但回归发现**表格题**退步——表格被 ■ 切碎，表格行与表头分离，表格语义断裂。
- **v3-table（最终版，规则名 `m1-pdf-section-v3-table`）**：■ 边界 ∪
  **次级标题（N-N.）与表格行的联合检测**——表格整块保留、不按 ■ 硬切。
  transmission-001 达到 **r1**，全量回归不掉题。

最终效果：混动手册索引从 432 块 → **1486 块**（块更小更纯），
锁定集 22/22，golden 30/30。

### 3.6 学习要点

1. **诊断顺序**：先分路（full_text/vector 哪路错）→ 再定位（SQL 直查看原文）→
   数据问题就修数据，算法问题才修算法。
2. **切块是 RAG 里杠杆最大的环节**：embedding 质量上限由块内容纯度决定。
3. **版式即语义**：PDF 的标记符号（■●）、编号模式（N-N.）是免费的分割信号，
   比字符数上限可靠得多。
4. **每轮实验都要全量回归**：v2 的表格退步就是回归抓出来的。

## 第 4 章 索引代次：改切块为什么不用删库

**先修**：第 3 章。

切块规则改了，432 块的旧索引怎么办？最粗暴的做法是删库重导。
但那样会有一个「索引不存在」的窗口期，而且无法回滚。

本项目的**索引代次（generation）机制**：

1. **发布即快照**：一次「入库→切块→embedding→发布」产出一个不可变的代，
   每块记录所属页码、来源、代 id。
2. **配置指纹（fingerprint）**：把影响切块/embedding 的全部配置
   （含 chunker 版本串 `m1-pdf-section-v3-table`）哈希成指纹。
   **同指纹拒绝建新代**（防止手滑建出内容相同的代）；指纹变了说明切法变了，
   必须走重建。
3. **三步管理**（CLI）：
   `create-index-generation`（建空代）→ `rebuild-index-generation`
   （用**当前运行时代码**重新切块已入库的原文）→
   `activate-index-generation`（原子切换生效代）。
4. **检索只看激活代**：切换是原子的，切换瞬间前后请求各见完整的旧/新代，
   无中间态；出问题可切回旧代回滚。

**学习要点**：这是「不可变发布 + 原子切换」模式在检索系统上的应用。
代价是存储翻倍（新旧代并存），换来的是零停机、可回滚、可对比
（评测可以指定代来跑 A/B）。`rebuild` 用原文重切，PDF 只需入库一次——
**原文是唯一事实源，切块是可重算的视图**。

## 第 5 章 rerank：不动索引的查询时方案

**先修**：第 0 章（RRF）、第 3 章（索引 vs 查询时的区别）。

### 5.1 残余问题：RRF 的结构性盲区

v3-table + 词典 + 0.25 权重之后，仍有一类 miss：
vector 路明明把正确块排在 r2-r6，但 RRF 融合后被别的块挤出 top-k。
（典型如 gasoline 的 hood r11、maint r14、tow r9。）

这不是数据病（块很纯），也不是词典病（词都对），是 **RRF 融合的算术结果**——
「两路都不错但都不拔尖」干不过「单路第一」。要救它只有两条路：

- **路线 A：动索引/融合算法**——重调权重？为个别题重切索引？全局影响大，
  锁定集已绿的 22 题全要重验。
- **路线 B：查询时重排（rerank）**——检索照旧出 top-16（深池），
  再用一个 LLM 对这 16 块**按与问题的相关度重新排序**，取前 8。
  只影响这一问的排序，机制上跨问题隔离（A 题的重排不改变 B 题的索引）。

选了 **B**。理由：风险局部化 + 可逐题验证。

### 5.2 架构决策：又一次「调用方组合层」

rerank 没有进核心库 `know_one/retrieve`，而是独立模块
`know_one/rerank.py`，由**调用方**（评测脚本、回答脚本）显式组合：

```
hybrid 检索(深池 16) ──> Reranker.rerank(query, evidence) ──> top-8
```

和第 2 章词典同一个模式：**检索是库的职责，重排是应用的策略**。
库不依赖任何 LLM 端点；不要 rerank 的调用方零成本。

### 5.3 listwise：一次问完，而不是逐块问

重排有两种问法：

- **pointwise**：每块单独问「这段和问题相关吗？」打分。16 块 = 16 次调用，
  慢、贵、且分数不可跨块比较。
- **listwise**：把 16 块（每块截断 180 字）拼进一个 prompt，
  让 LLM 直接输出排序 `[9, 1, 2, ...]`（块编号序列）。**一次调用**。

实现要点（`know_one/rerank.py`）：

- LLM 端点走 OpenAI 兼容 `/chat/completions`（LM Studio 本地 qwen 模型），
  `temperature=0`（排序要确定性）；
- 输出用正则提取 JSON 数组，容忍 markdown 代码围栏；编号越界自动过滤；
- **降级设计**：网络失败/超时/解析失败时，`rerank()` 返回 **RRF 原序**
  并打 `degraded` 标记。**重排是增强，永远不能比不重排更差**——
  这是这个模块的安全底线。

### 5.4 一个真 bug：深池放水

第一次接进评测器时发现分数虚高：重排取的是 top-16 深池，
但判定命中却对着重排后的 top-16 看——等于把 top-k 从 8 放水到 16。
修复：**评测口径必须截回 top-k 再判定**（重排后取前 8 判，深池只是重排的输入）。
修复后才是真实的 30/30。

**学习要点**：评测器自身的口径 bug 会让一切优化变成自欺。
「结果变好」先问一句：判定标准变了吗？

## 第 6 章 safety-001 负迁移：blend 的诞生

**先修**：第 5 章。这是全项目最有教学价值的一章：**优化手段自己也会犯错**。

### 6.1 症状：rerank 救活了 4 题，却弄坏了 1 题

纯 LLM 替换式重排上线后，golden 30 题里 signal/fuse 等被救回，但：

- **safety-001**（问：「开车时能调驾驶座椅吗？」），
  正确答案块在 RRF 里排 **r2**——本来就在 top-8 里，根本不需要救。
- 手册答案是一段警告：「**驾驶过程中请勿**调节驾驶员座椅……」。
- LLM 重排把它判成与问题「相关性低」（问「能调吗」，答案是「勿调」，
  语义方向相反），挤到 **r10/r11** → miss。

这个现象叫**负迁移（negative transfer）**：为 A 类问题设计的优化，
对 B 类问题产生了反效果。否定式安全问题的语义偏差（问句与答案的
表面语义相反）是 LLM 相关性判断的系统性弱项，改 prompt 措辞无效。

### 6.2 实验矩阵：用数据选方案，不用感觉

把当时全部 52 道历史评测题拉出来，对每题记录
`(RRF 排名, LLM 排名)` 两个坐标，然后模拟不同策略的命中率：

| 策略 | 命中 |
|---|---|
| 纯 RRF（不重排） | 48/52 |
| 纯 LLM 替换 | 51/52（救回 3 题，弄丢 safety-001） |
| **blend(4,4)** | **52/52** |

这就是**排名矩阵实验法**：一次采集原始数据，离线模拟所有候选策略，
不反复跑昂贵的在线评测。还给 blend 做了**抖动实验**——把 LLM 排名
人为扰动 ±2 位再模拟，blend 仍 52/52（而 (6,2) 名额配置抖动下会掉题），
证明选择 4/4 不是过拟合。

### 6.3 blend 语义：并集 + 硬下界

最终实现（`RerankConfig.llm_reserve=4, rrf_reserve=4`）：

```
最终顺序 = LLM 前 4 名（推荐，救语义召回）
        + RRF 前 4 名中未入列的块（保底，护住本来就对的）
        + 其余块按 RRF 原序
```

两条性质：

1. **硬下界**：RRF 前两名**必然**进最终前 8——LLM 就算完全判错，
   也**不可能**把一个 r2 的块挤出 top-8。safety-001 从此免疫。
2. **无冲突**：实测 blend 与纯替换的前 4 位完全一致——
   说明 4 个名额已覆盖 LLM 的全部增量价值，剩下的名额纯粹是保险。

一次 LLM 调用同时服务两个目标（推荐+保底），失败仍整体降级 RRF 原序。
终验：golden 30/30 零降级，锁定集 22/22。

### 6.4 学习要点

1. **优化上线前，先看它会不会伤已经在好的题**——「救回 4 丢 1」可能是净亏。
2. 对抗 LLM 判断失误最稳的不是更好的 prompt，而是**结构上让它只拥有有限权力**
   （reserve 名额制 = 权力上限）。
3. 排名矩阵 + 抖动模拟，是低成本高置信的方案选择法。

## 第 7 章 gasoline 手册：版式考古与「不动索引」决策

**先修**：第 3 章（切块）、第 5 章（rerank）。

第二本手册（汽油版 RAV4）接入后，摆着两条路：
A. 直接套用混动版经验重建 v3-table 索引；B. 先摸底再说。选了 B。

### 7.1 摸底：它和混动版是同族版式吗

先查库：432 块、p50 块长 519 字、页眉页码混入块首——
**这是 v1 粗切块时代的形态**（索引代次 fingerprint `82fc174e9646`，
还停在旧切法，没有随核心代码升级）。

再验版式：SQL 统计块文本中的标记字符——314 块含 ■、205 块含 ●，
与混动手册同族（这一步曾经因 ■/□ 码点混淆判错过，见 3.4 插曲）。
结论：v3-table 若要重建**可以直接适用**。但——要不要建？

### 7.2 基线数据说话

用 18 题最小评测集（构建流程见第 8 章）实测当前 v1 粗切索引：

| 模式 | 命中 | 分析 |
|---|---|---|
| full_text | 6/18 | 大块稀释词频信号，系统性弱势 |
| vector | 18/18 | **块虽粗但语义还在**——大杂烩块的问题在融合，不在召回 |
| hybrid | 15/18 | hood r11 / maint r14 / tow r9——全是第 5 章那种 RRF 挤出型 |
| hybrid+rerank(blend) | **18/18** | 三个 miss 全在深池 top-16 内，blend 直接拉回 |

### 7.3 决策：不重建索引

v1 粗切块的「病」（块大、页眉污染）在这 18 题护栏下**没有可观测的伤害**：
vector 满分说明召回无碍；融合损失由 rerank 补齐且零降级。
重建 v3-table 要花全量重切+重嵌+全量回归的成本，收益为 0。

于是 v3-table 重建**降级为可选技术债**，并写下明确触发条件：
出现 full_text 依赖场景（如无 embedding 服务的降级检索）或块污染病历时再建。
（注：full_text 6/18 在纯 v1 大块下的弱势是已知形态，但部署口径不走纯全文路。）

### 7.4 学习要点

1. **「上次怎么修的」不等于「这次也要这么修」**——先摸底，让基线数据决定。
2. 「简单优先」不是偷懒：不动的成本是 0，收益用护栏证明也是 0 损失，
   这就是正确决策。技术债的关键是**写清触发条件**，而不是排队假装要还。

## 第 8 章 评测集治理：draft → approved → v1

**先修**：第 1 章。

新增一个评测集（以 gasoline 18 条为例）的完整流程：

1. **draft 起草**：从当前索引块原文里逐字摘期望短语 + 记录页码，
   写成 `gasoline_smoke_draft.jsonl`（`review_status: "draft"`）。
2. **自动校验**（机器能查的先查）：脚本验证每个短语确实是当前索引块原文
   （空白归一后逐字匹配）、页码与块页码一致。18/18 通过。
3. **人工复核**（机器不能替的）：人看两件事——
   **问题自然度**（是真用户会问的话，还是为凑原文生造的）和
   **短语充分性**（命中这个短语是否等于找到了答案）。
   复核中就抓出过两条边缘案例（#3 短语被括注截断、#13 只是功能名非答案）。
4. **approved**：人工通过后逐行把 `draft` 改 `approved`（精准子串替换，
   不整行重序列化——保留原始键序，diff 最小）。
5. **版本化锁定**：复制为 `gasoline_smoke_v1.jsonl` 冻结。
   `_v1` 是「经复核的这一版」，未来增删出 `_v2`，不回头改 v1。

**学习要点**：评测集是资产，质量劣化比缺集更危险（它会把错误方向合法化）。
机器校验（可自动化的客观标准）与人工复核（主观判断）各守一层，
版本化让历史分数永远可解释。

## 第 9 章 运维教训：同实例互扰

**先修**：无。一个「代码没错、环境错了」的案例。

某次回归中，锁定集（本应稳定 22/22 的裸基线）偶发掉到 22→20。
代码与索引都没动过。排查方向转向环境：

- embedding 和 rerank 都指向**同一台 LM Studio 实例**（`192.168.2.6:1234`）；
- 批量评测时，rerank 的 LLM 推理与 embedding 请求在同一实例上**抢算力**，
  embedding 超时/降速 → 部分块嵌入质量下降 → 排名抖动；
- **对照实验**：空闲时段复跑同一锁定集，恢复 22/22——实锤互扰。

处置：评测期间避免同实例并发；长期方案是 embedding 与 rerank 分实例部署
（尚未执行，是遗留运维项）。

**学习要点**：分数异常时，改动清单之外还有三个嫌疑人——**环境（资源/网络）、
依赖服务（LLM/embedding 端点）、时间（缓存/并发窗口）**。
「复跑一次」是最便宜的去疑手段；好排查的标准是能设计出**对照实验**。

## 附录 A 术语表

| 术语 | 含义 |
|---|---|
| RAG | 检索增强生成：先检索证据再让 LLM 引用作答 |
| 切块 | 把长文档切成检索粒度的块；RAG 中影响最大的数据环节 |
| 块污染 | 单块混入过多不相关内容，语义信号被稀释，embedding 质量下降 |
| embedding | 文本压缩成的语义向量；语义相近的文本向量距离近 |
| 余弦相似度 | 两向量夹角衡量语义相近度，向量检索的打分方式 |
| tsvector / 全文检索 | PostgreSQL 的分词倒排索引，按词精确匹配 |
| RRF | 倒数排名融合：`权重/(60+排名)`，按排名而非分数融合两路结果 |
| top-k / recall_threshold | 只取检索结果前 k 个；评测判定窗口 |
| rank (r1/r12) | 期望块在结果中的实际名次 |
| miss / 命中率 | 期望块未进 top-k / 命中题数占比 |
| 深池 | 重排取的候选池（16），比最终 top-k（8）深 |
| rerank / 重排 | 用 LLM 对候选块按相关度重新排序的查询时增强 |
| listwise / pointwise | 一次对全部候选排序 / 逐个打分；前者一次调用且分数可比 |
| blend | 本项目最终排序：LLM 前 4 ∪ RRF 前 4 保底 + 其余 RRF 原序 |
| reserve | blend 的名额参数：llm_reserve/rrf_reserve（4/4） |
| 降级 | rerank 失败时回退 RRF 原序并打 degraded 标记 |
| 负迁移 | 某 A 类优化对 B 类问题产生反效果（如 safety-001） |
| 词典扩展 / 查询扩展 | 检索前把口语词补全为手册术语（转向灯→转向信号灯） |
| 索引代 | 一次「入库→切块→嵌入→发布」的不可变快照 |
| fingerprint | 影响切块/嵌入的配置哈希；同指纹拒建新代 |
| activate | 原子切换当前生效的索引代；支持回滚 |
| 锁定集 | 版本化冻结的评测集，任何改动的回归护栏 |
| review_status | 评测条目状态：draft（自动校验过）→ approved（人工复核过） |
| expected_any | 期望短语组（逐字摘自原文，空白归一匹配；多短语 AND） |
| 版式标记 | ■ (U+25A0) / ● (U+25CF)：丰田手册的条目分隔体系，天然切块边界 |
| 排名矩阵 | 对每题记录 (RRF 排名, LLM 排名) 后离线模拟各策略的实验法 |
| LM Studio | 本地 LLM 服务（OpenAI 兼容 API），承载 embedding 与 rerank 模型 |
